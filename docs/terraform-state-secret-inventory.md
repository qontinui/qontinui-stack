# What is in terraform state, and why it cannot leave

**Status: current as of 2026-08-20.** Produced as P1 of plan
`2026-08-15-terraform-plan-infra-observer-phase-3b`, which needed a decision on
whether the full-`terraform plan` drift observer could safely run in CI.

**Answer: it cannot, and the reason is durable.** Every one of the 12
`aws_secretsmanager_secret_version` values in `aws/` is generated *by terraform*
and is *live*, so it lives in state as plaintext and will keep living there
until someone rotates it. This document is the evidence for that claim and the
per-secret disposition table it produces.

## The one-paragraph version

`a0d6016` established the pattern for getting a secret out of state: replace the
managed `aws_secretsmanager_secret` + `_secret_version` pair with a
`data "aws_secretsmanager_secret"` lookup, drop both resources with `removed`
blocks (`destroy = false`) and `terraform state rm`. `485031d` then deleted the
one-shot blocks. That pattern works only for a value terraform does **not**
generate — and it has already been applied to every such value. What remains is
12 values that terraform itself creates via 6 `random_password` resources.
Converting those to data sources moves the secret without removing it, because
`random_password.<x>.result` is a plaintext state attribute in its own right.
Removing them for real means the values must be generated somewhere else, which
is a rotation — a separate change with a separate blast radius.

## Evidence 1 — all 12 are terraform-generated

Traced through the module inputs on `origin/main`, 2026-08-20:

| `aws_secretsmanager_secret_version` | `secret_string` | Ultimately generated by |
|---|---|---|
| `modules/coord` `database_url` | `var.database_url` ← `module.postgres.connection_string` | `random_password.master` |
| `modules/coord` `redis_url` | `var.redis_url` ← `module.redis.connection_string` | `random_password.auth` |
| `modules/coord` `coord_admin_secret` | `var.coord_admin_secret` | `random_password.coord_admin_secret` |
| `modules/coord` `web_service_secret` | `var.coord_web_service_secret` | `random_password.coord_web_service_secret` |
| `modules/migrator` `database_url` | `var.database_url` ← `replace(replace(module.postgres.connection_string, "postgres://", "postgresql://"), "%", "%%")` | `random_password.master` |
| `modules/postgres` `master` | `jsonencode({… password = random_password.master.result …})` | `random_password.master` |
| `modules/redis` `auth` | `random_password.auth.result` | `random_password.auth` |
| `modules/tunnel` `metrics_token` (SM name `qontinui/<env>/coord/metrics_token` — the module label and the secret name differ) | `var.metrics_token` | `random_password.coord_metrics_token` |
| `modules/web` `database_url` | `var.database_url` ← `replace(replace(module.postgres.connection_string, "postgres://", "postgresql://"), "?sslmode=disable", "")` | `random_password.master` |
| `modules/web` `coord_admin_secret` | `var.coord_admin_secret` | `random_password.coord_admin_secret` |
| `modules/web` `coord_web_service_secret` | `var.coord_web_service_secret` | `random_password.coord_web_service_secret` |
| `modules/web` `secret_key` | `var.secret_key` | `random_password.web_secret_key` |

Six generators: `random_password.master` (`aws/modules/postgres/main.tf`),
`random_password.auth` (`aws/modules/redis/main.tf`), and
`coord_admin_secret` / `coord_web_service_secret` / `coord_metrics_token` /
`web_secret_key` (all `aws/staging/main.tf`).

## Evidence 2 — the "externally owned" class is empty because it is already drained

The three `data "aws_secretsmanager_secret"` lookups in the tree are the entire
externally-staged population, and all three are already converted:

| Value | Where |
|---|---|
| `coord/webhook_secret` | `aws/modules/coord/main.tf` — *"Operator-staged out-of-band; this data source resolves it by name at plan time."* |
| `coord_jwt_signing_key` (SM name `qontinui/<env>/coord_jwt_signing_key` — flat, no `coord/` segment) | `aws/modules/coord/main.tf` |
| `web/redis_url` | `aws/modules/web/main.tf` |

So there is no easy tranche left. The `a0d6016` treatment applies to **none** of
the remaining 12.

## Evidence 3 — terraform's copies are LIVE, not stale

`aws/modules/postgres/main.tf` carries
`lifecycle { ignore_changes = [password] }` with the comment *"rotate via
Secrets Manager rotation, not TF"*. That comment describes an intended posture,
and it raised a real question: if the live password had since been rotated out
of band, terraform's copy would be a **dead string** rather than a live
credential, and removing it would be safe without rotating anything.

It has not been. Read from Secrets Manager metadata only — `describe`/`list`,
never `get-secret-value`, so no value was fetched — in **us-east-1** (the stack's
region; the CLI default profile here is `eu-central-1`, where the same query
correctly returns nothing and would be misread as "no secrets"):

- `LastRotatedDate` is `null` for **every** secret in the account.
- `RotationEnabled` is `null` (never configured) for every secret.
- `qontinui/staging/postgres/master` — `LastChangedDate 2026-05-17T10:41:54`,
  matching its `CreatedDate` to the second.
- `qontinui/staging/redis/auth` — `LastChangedDate 2026-05-17T10:41:53`, same.

Reproduce with:

```bash
aws secretsmanager list-secrets --region us-east-1 \
  --query 'SecretList[?LastRotatedDate!=`null`].Name'
```

An empty result there means "no secret has ever been rotated". Note this is a
paginated call and the filter applies per page, so read it as the corroborating
signal it is, alongside the per-secret `LastChangedDate` values above.

**Verdict: every generated value in state is the live credential.** The
`ignore_changes` comment documents a rotation posture that has never once been
exercised.

## The disposition table

`convert` = the `a0d6016` data-source treatment. `must-stay` = cannot leave state
without rotating the value first.

| # | secret_version | Generator | TF copy live? | Disposition |
|---|---|---|---|---|
| 1 | `postgres/master` | `random_password.master` | **live** | must-stay |
| 2 | `redis/auth` | `random_password.auth` | **live** | must-stay |
| 3 | `coord/database_url` | derived from #1 | **live** | must-stay (derived) |
| 4 | `migrator/database_url` | derived from #1 | **live** | must-stay (derived) |
| 5 | `web/database_url` | derived from #1 | **live** | must-stay (derived) |
| 6 | `coord/redis_url` | derived from #2 | **live** | must-stay (derived) |
| 7 | `coord/coord_admin_secret` | `random_password.coord_admin_secret` | **live** | must-stay |
| 8 | `web/coord_admin_secret` | same generator as #7 | **live** | must-stay |
| 9 | `coord/web_service_secret` | `random_password.coord_web_service_secret` | **live** | must-stay |
| 10 | `web/coord_web_service_secret` | same generator as #9 | **live** | must-stay |
| 11 | `web/secret_key` | `random_password.web_secret_key` | **live** | must-stay |
| 12 | `tunnel/metrics_token` | `random_password.coord_metrics_token` | **live** | must-stay |

Twelve rows, twelve `must-stay`. A phase that converted eleven and quietly left
the twelfth would not have done this work; neither would one that converted all
twelve and left six `random_password` resources holding the same plaintext.

### Three more copies the `secret_version` table does not cover

The twelve rows above are the `aws_secretsmanager_secret_version` resources. The
same plaintext values also sit in **three consumer resources**, which the
data-source conversion recipe below would leave behind entirely:

| Resource | Attribute | Note |
|---|---|---|
| `aws_db_instance.main` (`aws/modules/postgres/main.tf`) | `password = random_password.master.result` | `lifecycle { ignore_changes = [password] }` suppresses the *diff*, not the state attribute |
| `aws_elasticache_replication_group.main` (`aws/modules/redis/main.tf`) | `auth_token = random_password.auth.result` | same pattern |
| `aws_lb_listener_rule.coord_metrics_authed` (`aws/modules/tunnel/main.tf`) | `condition { http_header { values = [var.metrics_token] } }` | **the sharpest one** — a live bearer token stored verbatim as an ALB routing condition, in a resource nobody would grep for when hunting secrets |

This does not weaken the conclusion; it strengthens it. It does mean the recipe
in "What follows from it" §4 is under-specified as written: removing a value
from state is not "convert the pair and delete the generator", it is that plus
every consumer that interpolates the generator's `.result`.

## What follows from it

1. **The full `terraform plan` must never run in GitHub Actions on this repo.**
   `qontinui-stack` is public. A plan refreshes all 12, and the S3 state object
   already contains them, so `-refresh=false` does not help. Terraform redacts
   attributes it knows are `sensitive`, which is a mitigation and not a
   guarantee — and the unmarked-attribute case is **not hypothetical here**:
   `aws_sns_topic_subscription.budget_email` (`aws/modules/cost-control/main.tf`)
   has `endpoint = var.alert_email`, and `variable "alert_email"` is declared
   without `sensitive = true`, so the operator's address renders unredacted in
   any plan diff touching it. (The asymmetry looks deliberate —
   `variable "signup_allowlist"` in `aws/modules/cross-idp-linking` *is* marked
   sensitive and does get redacted — but it is a present PII residual, not a
   future risk.) `pull_request_target` is forbidden outright: it would hand
   fork-authored code the secret-bearing context.
2. **`.github/workflows/qontinui-ci.yml` is credential-free and stays that
   way.** It runs `terraform fmt -check -recursive` and
   `terraform init -backend=false` + `validate` — source-only checks that need
   no AWS principal and fetch no state — plus the drift classifier's unit tests.
3. **The drift observer runs out of CI.** `scripts/terraform-plan-drift.py`
   runs on a box that already holds these credentials and POSTs only a
   classification to coord's `POST /coord/infra/plan-drift`. It introduces no
   new IAM principal; its only new secret is the shared `COORD_INGEST_TOKEN`.
4. **De-secreting state is a real, separable piece of work, and it is a
   rotation plan.** It would generate each value out of band, stage it in
   Secrets Manager, convert the resource to a data source, `state rm` the pair,
   delete the `random_password` resource, **and re-point the three consumer
   resources above at the data source** — otherwise the value stays in state
   under a different address. Twelve values, six generators, three consumers, a
   restart of everything downstream. That is not this plan's scope and should
   not be smuggled into it.

## Scope note

`cognito_user_pool_arn` (`aws/staging/variables.tf`) is *"MANUALLY managed and
intentionally NOT in Terraform"*. That is a **scope** property of the estate,
not a coverage deduction on the observer: coord's `coverage` field is an
observer-relative completion fraction ("did I finish my own checks?"), not a
fraction of the estate. A plan that ran to completion reports `1.0` honestly.
